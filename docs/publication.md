# 公開と記事の方針

## 読者と著者の立ち位置

OIDCの用語を理解し、消費者向けサービスの認証基盤の容量や負荷試験を任されるバックエンドエンジニア・SRE・テックリードを対象とする。

タイトル案：**「ログイン数だけで認証基盤を設計してよいのか？KeycloakでOIDCの混在負荷を測る」**

読者が持ち帰るものは、フロー別の負荷モデル、誤測定を避けるスクリプト、単独と混在の比較、判断の限界。著者のプレゼンスは「OIDCを設定できる」だけでなく「測定の前提を設計し、観測から説明できる」ことで示す。反響や競合優位を保証するものではない。

## 記事の流れ

1. 実測が得られたら、最も説明力のある結果図と問いを冒頭へ置く。
2. 想定サービスでログインと更新が別の負荷になることを説明。仮の利用者数から出す値は理論として表示。
3. 構成図、実験条件、Code + PKCEのシーケンス、セッションの概念ER。
4. 単独・混在・集中の全結果。失敗した試行と生成器上限も掲載。
5. CPU/DB/GC等から言えることと、原因を確定できないことを分ける。
6. 本番へ持ち帰る負荷試験手順と、Mac単体で検証していない領域を説明。
7. 再現リポジトリと実行コマンド。

差が出ない場合も有効な結果。タイトルに「更新がログインを止めた」などの結論を先に置かない。大規模本番の運用実績や実ユーザー数を示唆しない。以前のキャッシュTTL検証は本記事の中心に戻さない。

## Public repoの作り方

`public_bundle.py --export` の生成先だけを新規リポジトリへコピーする。Git初期化・remote設定・pushはこのキットのコマンドでは行わない。個人情報を含む親ディレクトリの履歴も持ち込まない。

コードはMIT License。Keycloak・PostgreSQL・k6のバイナリやコンテナを同梱せず、利用者が元の配布元から取得する。各依存物のライセンスは各配布元に従う。

初期の公開対象には結果を含めない。実測後、必要な集計表・図と手入力の環境条件を別途レビューして加える。`results/`、DBダンプ、import、.env、生ログを丸ごと追加しない。パターン検査は補助であり、機密情報がないことの数学的な保証ではない。

## 結果を公開するときに必要な情報

- SoCモデル、メモリ量、macOS/Dockerバージョン、VM CPU/メモリ配分。ホスト名・シリアル番号・個人パスは不要。
- イメージのID/取得digest、負荷設定、ハッシュ設定、初期セッション数、試行順。
- 全試行の成功数/失敗数、p95/p99、dropped iterations、生成器と対象の資源。
- 観測の欠落、途中終了、閾値超過、差が出なかった条件。
- TLSや外部IdP等が含まれないこと。

`aggregate.json` は固定フィールドだけに集計するが、公開時は値と記述を確認する。スクリーンショットや生ログより、必要な数値から描き直した図を優先する。
