# 公開と記事の方針

## 読者と著者の立ち位置

一般消費者向けサービスで、ログイン実装から認可・可用性・運用を含む構成へ進みたいバックエンドエンジニア・テックリード向け。

主記事は [KeycloakとOpenFGAによるアーキテクチャ](../article/qiita.md)。写真アルバム共有を例に、認証と認可の責任分担、データ整合性、ローカル・GCP・AWS・Azureの配置を説明する。既存実験は認証部分を測った補足として流用し、詳しい測定方法は [別資料](../article/oidc-measurement.md) に残す。

読者が持ち帰るものは、構成の選択理由、実装する責任の境界、非機能要件、動作・負荷・障害を確かめる順序。著者の強みを、部品の紹介に加えて、権限変更や障害で破綻しやすい点まで説明することに置く。市場の独占性や反響を実証したという意味ではない。

## 記事の流れ

1. Keycloak・OpenFGA・業務APIの役割を全体図で説明。
2. 守る要件と、1回のアクセスの通信図。
3. 認可モデル、業務側ER、共有解除の反映。
4. 測定済み範囲を示すローカル図と、3クラウドの配置案。
5. 非公開経路、DB、秘密情報、可用性、障害の影響。
6. Mac miniで測定済みの認証部分と、その限界。
7. 未実装の認可やクラウドを追加する際の試験、実行できるキット。

認可モデルとクラウドは設計案。構築済み・検証済みと書かない。実測の不一致や監視欠落を削らず、本番容量へ外挿しない。

## Public repoの作り方

`public_bundle.py --export` の生成先だけを新規リポジトリへコピーする。Git初期化・remote設定・pushはこのキットのコマンドでは行わない。個人情報を含む親ディレクトリの履歴も持ち込まない。

コードはMIT License。Keycloak・PostgreSQL・k6のバイナリやコンテナを同梱せず、利用者が元の配布元から取得する。各依存物のライセンスは各配布元に従う。

現在の公開対象はコードとレビュー済みの集約結果・図・記事。新しい結果も必要な集計表・図と環境条件をレビューしてallowlistへ加える。`results/`、DBダンプ、import、.env、生ログを丸ごと追加しない。パターン検査は補助であり、機密情報がないことの数学的な保証ではない。

## 結果を公開するときに必要な情報

- SoCモデル、メモリ量、macOS/Dockerバージョン、VM CPU/メモリ配分。ホスト名・シリアル番号・個人パスは不要。
- イメージのID/取得digest、負荷設定、ハッシュ設定、初期セッション数、試行順。
- 全試行の成功数/失敗数、p95/p99、dropped iterations、生成器と対象の資源。
- 観測の欠落、途中終了、閾値超過、差が出なかった条件。
- TLSや外部IdP等が含まれないこと。

`aggregate.json` は固定フィールドだけに集計するが、公開時は値と記述を確認する。スクリーンショットや生ログより、必要な数値から描き直した図を優先する。
