# 実験設計

## 命題

「ログイン数だけでOIDC認証基盤をサイジングしてよいのか？」を、ログイン単独・更新単独・混在・更新の時間的集中で検討する。

Keycloak公式にも大規模環境での[ログインと更新の性能測定](https://www.keycloak.org/2025/10/keycloak-benchmark)がある。本記事の価値は最大TPS記録ではなく、読者が小さな環境で負荷条件を変え、許容範囲と悪化の原因を調べられることに置く。単一Macの値から必要本番Pod数を直接換算しない。

## 仮説と反証

1. 更新負荷を加えると、同じログイン到着率でもログインp99または成功率が悪化する可能性がある。差が出なければ、その負荷範囲では干渉を観測しなかったと報告する。
2. 平均更新件数が等しくても時間的集中で遅延・失敗が増える可能性がある。平均値だけではなく時系列を見る。
3. 最初に上限へ達する箇所がKeycloak CPUとは限らない。DB、JVM、負荷生成器、VM資源を観測し、因果は追加の一変数比較で確かめる。

## 固定条件

| 条件 | 初期値・扱い |
|---|---|
| ユーザー | 架空1,000人、外部メール送信なし |
| フロー | パスワード入力を伴うAuthorization Code + PKCE S256、openid scope |
| セッション | VUS×2件を毎回事前作成。既定200件。login単独でも同じ件数 |
| 更新 | VUごとに独立セッション。RT rotation有効、再利用0 |
| アクセストークン | 300秒。負荷生成の更新タイミングはTTLとは独立 |
| セッション寿命 | idle 2時間、max 4時間。setup中の初期セッション失効を避ける |
| パスワード | Argon2、iterations 5を設定。他のArgon2パラメータは固定Keycloak版の既定値。実行時設定も確認して記事へ記載 |
| HTTP | Docker内部HTTP、TLSオフ。外部IdP・MFA・描画なし |
| DB | PostgreSQL単一、共有バッファ256MB、KC接続プール上限20 |
| キャッシュ | 固定Keycloak版の既定値。各run DB初期化、事前セッション作成後に60秒warmup |
| 生成器 | k6、全VU事前割当、一定/変動到着率。既定各シナリオ100VU |
| リトライ | 自動再ログイン・アプリ再試行なし。RT更新失敗後はそのVUを失敗扱いで維持 |

最後の条件は、ローテーション結果不明のRT再利用で成功率を偽らないため。`lab_errors` の `session_lost` が増えた実験は、継続的な正常更新の容量測定として使わない。先行するHTTP失敗を調べ、負荷を下げた別試行を残す。

ログイン側は更新用アカウント以外を順番に再利用し、毎回cookieを消してパスワード認証する。ログイン成功でセッションは増える。ログアウトは追加負荷になるため測定中に挟まない。このセッション増加もログイン集中の一部であり、run間はDB初期化で揃える。固定セッション数の定常状態や長時間soakの証明ではない。

## 非機能の受入条件

以下は実験用の暫定判定基準であり、業界標準や実サービスのSLOではない。

| 観点 | 判定・証拠 |
|---|---|
| 機能正当性 | smokeでコード交換と更新が成功。state/nonce/issuer/audience/有効期限を確認。署名検証は生成器で行わず、完全なOIDC RP適合試験とは扱わない |
| 成功率 | 測定区間の各フロー99%以上。失敗を含む総試行数を分母にする |
| 遅延 | login p99 < 2,000ms、refresh p99 < 500ms。失敗込みと成功限定を分ける |
| 負荷成立 | dropped_iterations=0、予定件数と実行件数を比較。足りない場合は生成器/VU/対象の遅延を調査 |
| 資源 | KC・DB・k6のCPU/メモリ、KC GC/プール、DB活動数/ロック待ち/累積I/O統計を5秒程度ごとに収集 |
| 回復性 | 本編必須は負荷を下げた新しいrunが正常に終わること。停止/再起動中の可用性は今回測定しない |
| 再現性 | バージョン・イメージID・VM配分・Mac SoC・入力率・試行順・全試行結果を記録 |
| 情報管理 | 実ユーザーなし、秘密値自動生成、loopback公開、公開用ファイルをallowlistで抽出 |
| 限界 | HA/RPO/RTO、DoS防御、外部IdP、TLS、MFA、本番の同時利用者数への換算は対象外 |

`docker stats` のCPU 100%は通常1コア相当。2CPUのKeycloakの上限は約200%として解釈する。VM全体の競合やMacのメモリ圧迫もActivity Monitorで確認し、個人情報を含む画面をそのまま公開しない。

観測器はホストで動き、DBへ少量の照会をする。この観測自体の影響もある。5秒集計では短いスパイクを捉えきれない。CPU上限到達との相関だけで「CPUが原因」と断定しない。

## 土日：目安14時間

| 時間 | 作業・終了条件 |
|---|---|
| 土曜前半 2h | Docker設定、init/check、smoke。失敗すればここを直す。数値取りに進まない |
| 土曜中盤 2h | login 1→5→10→20 flows/s、refresh 5→20→50→100/s等の低い段階から探索。これは順序例で、最大値の保証なし |
| 土曜後半 3h | 単独両方が閾値内となるL/Rを選ぶ。login/refresh/mixed/mixed-burst各1回。毎回同じVUSとVM設定 |
| 日曜前半 3h | 選んだ4条件を各3回になるまで追試。順序を変える。1回目 L/R/M/B、2回目 B/M/R/L、3回目 R/B/L/M |
| 日曜中盤 2h | 全試行を集計。中央値と最小最大を提示。p99を全試行で平均して代表値にしない |
| 日曜後半 2h | 構成・フロー図と結果を記事へ。公開用書き出し、記録の確認 |

単独で閾値を超えたら、その上の段階へ進めない。k6の資源不足か対象サーバの上限か不明なら、負荷を下げるか、CPU配分の一変数比較を追加する。VU数変更時は事前セッション数も変わるため、それまでの条件と同列に比較しない。

4条件×3回の測定区間自体は36分＋warmup12分だが、毎回のDB/ハッシュ/セッション初期化、診断、再試行が別途必要。予定時間を超える場合はburstを次回へ送り、3条件×3回を完成させる。
